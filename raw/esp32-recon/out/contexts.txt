    13|

    16|| ESP32-C3 | ~10-15 uA | 1.0g (bare) | ESP-IDF SPI | ~2 EUR |
    17|| ESP32-S2 | ~20 uA | 1.5g | ESP-IDF SPI | ~3 EUR |
    18|| ESP32-S3 | ~10 uA | 2.0g | ESP-IDF SPI | ~4 EUR |
    19|| nRF52840 | ~1.5 uA | ~1g | Zephyr SPI | ~5 EUR |
    20|| STM32L4 | ~0.5 uA | ~0.5g | HAL SPI | ~3 EUR |

    34|- Deep Sleep nicht ganz so niedrig wie STM32L4 oder nRF52 (~10uA vs ~1uA)

    1|# ADR 004: 3D Yagi-Antennen-Struktur (4 Wings + Hub)
    2|
    3|## Status
    4|Akzeptiert
    5|
    6|## Kontext
    7|Der Ballon muss in mehrere Raumrichtungen funken koennen, da er sich dreht, pendelt und die Bodenstation an verschiedenen Positionen stehen kann. Eine einzelne omnidirektionale Antenne hat keinen Gewinn. Eine Patch-Antenne wurde evaluiert aber verworfen.
    8|
    9|## Entscheidung
    10|**4 identische Wing-Boards** mit je einer PCB-Yagi-Antenne, die orthogonal in verschiedene Raumrichtungen zeigen. Verbunden durch ein zentrales Hub-Board ueber Loetstellen. SP4T RF-Switch fuer "Leuchtturm-Modus" (Round-Robin TX).
    11|
    12|## Alternativen
    13|
    14|| Option | Gewinn | Gewicht | Polarisation | Komplexitaet |
    15||--------|--------|---------|-------------|-------------|
    16|| **4x Yagi 3D** | ~6-9 dBi pro Antenne | ~3.2g (PCBs) | Linear | Mittel (SP4T) |
    17|| Circular Patch | ~6-9 dBi | 0g (geaetzt) | Zirkular | Niedrig |
    18|| Cloverleaf | ~2 dBi | ~1.5g | Zirkular | Niedrig |
    19|| Dipol/Monopol | ~2 dBi | ~0.5g | Linear | Sehr niedrig |
    20|| 4x Yagi flach | ~6-9 dBi | ~3g | Linear | Mittel |
    21|
    22|## Begruendung fuer 4x Yagi 3D
    23|
    24|1. **Maximaler Gewinn**: ~6-9 dBi pro Yagi vs ~2 dBi bei omnidirektionalen Antennen
    25|2. **3D-Abdeckung**: Durch orthogonale Anordnung zeigen die Yagis in verschiedene Raumebenen, nicht nur in eine flache Ebene
    26|3. **Dual-Purpose PCBs**: Wing-Boards tragen gleichzeitig Solarzellen
    27|4. **3D-Solarernte**: 4 Wings in 4 Winkeln = fast immer mindestens 1-2 Wings in direktem Sonnenlicht
    28|5. **Identische Boards**: 4x das gleiche Wing-Board = einfachere Fertigung
    29|6. **Mechanische Stabilitaet**: Kreuzfoermige 3D-Struktur ist selbsttragend
    30|7. **Experimentell**: Leuchtturm-Modus mit SP4T ist ein spannendes RF-Experiment
    31|
    32|## Warum nicht Patch-Antenne
    33|Obwohl eine zirkular polarisierte Patch-Antenne einfacher waere (kein Switch, immun gegen Drehung), wurde sich der Benutzer bewusst fuer das 4x Yagi 3D-Design entschieden wegen:
    34|- Hoeherer moeglicher Gewinn bei jeder einzelnen Richtung
    35|- Das 3D-Antennen-Array als Lern- und Experimentierplattform
    36|- Die Kombination aus Antennen und Solar auf denselben Boards
    37|
    38|## Leuchtturm-Modus (Round-Robin)
    39|```
    40|Sendezyklus:
    41|1. SP4T → Wing 1 (Nord) → TX Paket (enthilt Antennen-ID)
    42|2. SP4T → Wing 2 (Sued) → TX Paket
    43|3. SP4T → Wing 3 (Ost)  → TX Paket
    44|4. SP4T → Wing 4 (West) → TX Paket
    45|Bodenstation waehlt staerkstes Signal
    46|```
    47|
    48|## 3D-Assembly
    49|- 4 Wing-Boards stecken durch Slots im zentralen Hub-Board
    50|- Verbindungen werden verloetet (mechanisch + elektrisch)
    51|- RF, Power und Ground laufen ueber die Loetverbindungen
    52|- Hub-Board sitzt oben (nahe am Ballon), Wings breiten sich nach unten/ausen aus

    1|# ADR 007: Adaptive Protokoll-Strategie (LoRa/FLRC/Sub-GHz)
    2|
    3|## Status
    4|Akzeptiert
    5|
    6|## Kontext
    7|Der Ballon muss in verschiedenen Entfernungen zur Bodenstation kommunizieren koennen. Von direkt ueber Kopf (1-5 km) bis weit am Horizont (100-300+ km). Verschiedene LoRa-Modulationen bieten unterschiedliche Kompromisse zwischen Reichweite, Airtime und Stromverbrauch.
    8|
    9|## Entscheidung
    10|Die Firmware waehlt automatisch die optimale Modulation und Band basierend auf den aktuellen Bedingungen:
    11|
    12|## Modi
    13|
    14|| Modus | Frequenz | Modulation | Reichweite | Airtime (24B) | TX-Strom | Einsatz |
    15||-------|----------|-----------|-----------|---------------|---------|---------|
    16|| **FLRC Schnell** | 2.4 GHz | FLRC 1.3 Mbps | <30 km | ~1 ms | 31 mA | Direkt ueber Kopf |
    17|| **LoRa Nah** | 2.4 GHz | LoRa SF7 | ~50 km | ~50 ms | 31 mA | Sichtlinie nah |
    18|| **LoRa Mittel** | 2.4 GHz | LoRa SF10 | ~100 km | ~400 ms | 31 mA | Horizont naeher |
    19|| **LoRa Fern** | Sub-GHz | LoRa SF12 | ~300+ km | ~2 s | 120 mA | Maximale Reichweite |
    20|| **LoRaWAN** | Sub-GHz | SF7-SF12 (ADR) | Variabel | Variabel | 120 mA | TTN Gateway |
    21|
    22|## Adaptive Moduswahl
    23|
    24|```
    25|Moduswahl-Logik (vereinfacht):
    26|
    27|if (supercap_voltage < 3.5V) {
    28|    // Niedrige Energie → sparsamer Modus
    29|    mode = LORA_24GHZ_SF10;  // 2.4 GHz, mittlere Airtime, niedriger Strom
    30|} else if (last_known_distance < 30km) {
    31|    mode = FLRC_FAST;         // Blitzschnell, minimaler Strom
    32|} else if (last_known_distance < 100km) {
    33|    mode = LORA_24GHZ_SF10;   // Gute Balance
    34|} else {
    35|    mode = LORA_SUBGHZ_SF12;  // Maximale Reichweite, hoher Strom
    36|}
    37|
    38|// Fallback: Wenn keine Distanz bekannt → starte mit LoRa Mittel
    39|// Bodestation kann Modus-Wechsel-Kommando senden
    40|```
    41|
    42|## Begruendung
    43|
    44|1. **FLRC fuer naehe Distanzen**: Extrem kurze Airtime = minimaler Stromverbrauch
    45|2. **2.4 GHz LoRa fuer mittlere Distanzen**: 31 mA TX-Strom, weltweit lizenzfrei
    46|3. **Sub-GHz LoRa fuer ferne Distanzen**: Maximale Sensitivity (-141.5 dBm), +22 dBm PA
    47|4. **Energie-basierte Entscheidung**: Wenn Supercaps fast leer → kein stromhungriger Sub-GHz Modus
    48|5. **LR2021 unterstuetzt alle Modi**: Kein Chip-Wechsel noetig
    49|
    50|## LoRaWAN Integration
    51|- Zusaetzlich zur P2P-Kommunikation wird LoRaWAN (OTAA/ABP) unterstuetzt
    52|- Ermglicht Positionierung ueber TDoA (Time Difference of Arrival) durch TTN-Gateways
    53|- Der Ballon kennt seine Position nicht selbst → Position wird serverseitig berechnet
    54|- Nutzt The Things Network (TTN) als Backbone

    1|# ADR 009: V1 Omnidirectional Antennas with V2 Directional Upgrade Path
    2|
    3|## Status
    4|Accepted
    5|
    6|## Context
    7|
    8|The balloon needs 2.4 GHz antennas for the mesh internet transport link. The original design (ADR-004) specified 4x PCB Yagis with SP4T switching. However, the mesh vision changes the optimization target: **balloon-to-ground** is the primary link (not balloon-to-balloon), and the ground station has unlimited size/weight/power for antenna gain.
    9|
    10|A thorough product search and link budget analysis was conducted to determine whether directional antennas are needed on the balloon at all.
    11|
    12|### Link Budget Finding
    13|
    14|With an 18 dBi ground station Yagi (reasonable: ~1.5m, ~EUR 30-50):
    15|
    16|| TX Power | Balloon Antenna | Received @300 km | Best Modulation | Air Rate |
    17||----------|----------------|------------------|-----------------|----------|
    18|| +22 dBm (FEM) | Omnidirectional (2 dBi) | -109.6 dBm | SF9/1625 | 22 kbps |
    19|| +22 dBm (FEM) | Yagi (7 dBi) | -102.6 dBm | SF8/1625 | 38 kbps |
    20|
    21|22 kbps at 300 km with just a wire dipole and ground station gain. With 4x MultiWAN bonding: ~88 kbps aggregate. **Directional antennas on the balloon buy 2-3x throughput, but omni already works.**
    22|
    23|### Product Research Findings
    24|
    25|A comprehensive search for off-the-shelf 2.4 GHz CP patch antennas suitable for pico balloons found:
    26|
    27|| Product | Frequency | Polarization | Gain | Weight | Suitable? |
    28||---------|-----------|-------------|------|--------|-----------|
    29|| AliExpress FPC strips | 2.4 GHz | Linear (not CP) | ~1-2 dBi (despite "5 dBi" claim) | ~0.2g | Omnidirectional, no directional gain |
    30|| Foxeer Lollipop 2.4G | 2.4 GHz | RHCP | 2.6 dBi | ~3g each (x4 = 12g) | CP but omnidirectional, too heavy |
    31|| iFlight 2.4G CP panel | 2.4 GHz | RHCP/LHCP | ~5-8 dBi | ~15-25g | Too heavy for balloon |
    32|| Custom CP PCB patch | 2.4 GHz | RHCP | ~5-7 dBi | ~0.5g | Requires EM simulation + VNA tuning |
    33|| PCB Yagi (our design) | 2.4 GHz | Linear | ~6-9 dBi | ~0g (etched) | Already designed, works |
    34|
    35|**No commercially available lightweight 2.4 GHz CP directional patch antenna exists.** The market is dominated by 5.8 GHz (FPV drones) and GPS L1 (1.575 GHz). 2.4 GHz antennas are almost exclusively linear WiFi/BT antennas.
    36|
    37|### Balloon-to-Balloon Range
    38|
    39|At 12 km altitude, two balloons have a geometric line-of-sight of ~780 km. However, practical 2.4 GHz LoRa range at this distance requires directional antennas at both ends and is limited to SF12 (~0.25 kbps). The primary mesh links are balloon-to-ground (~300 km), not balloon-to-balloon.
    40|
    41|## Decision
    42|

    44|- 868 MHz: wire dipole, ~16.4 cm, ~2 dBi, omnidirectional, rotation immune
    45|- 2.4 GHz: wire dipole, ~6 cm, ~2 dBi, omnidirectional, rotation immune
    46|- Ground station: 868 MHz linear Yagi (~12 dBi) + 2.4 GHz CP helical (~14 dBi RHCP)
    47|- No SP4T switch, no antenna switching firmware, no wing board antenna design

    52|- Or custom CP PCB patches if VNA access available
    53|- SP4T switch + antenna diversity firmware
    54|- Throughput: ~38-87 kbps at 300 km (single link)
    55|- PCB designed to accommodate SP4T footprint and wing board connectors

    57|### Night-Off Default
    58|
    59|The balloon enters deep sleep at night (no solar). This is the default configuration:
    60|- Saves ~3.5g (smaller supercaps: 0.47F vs 3.3F, fewer solar cells: 6-8 vs 12)

    66|

    68||------|---------|-------------|------|------|---------|

    75|

    85|
    86|- V1 hardware is simpler: no SP4T, no wing board antenna design, no switching firmware

    88|- V2 upgrade path preserved in PCB layout (SP4T footprint, wing board connectors)
    89|- Ground stations need two antennas (868 MHz Yagi + 2.4 GHz helical)
    90|- Balloon rotation is handled at ground station (CP helical), not on balloon

    1|# ADR 012: Mesh Networking Strategy — FIPS + MeshCore + TollGate + Nostr
    2|
    3|## Status
    4|
    5|Accepted
    6|
    7|## Context
    8|
    9|The mesh stack needs networking, community engagement, a business model, and async messaging for balloon-based internet transport. The original ROADMAP.md Phase 4 proposed custom mesh routing, but FIPS (Free Internetworking Peering System) already provides self-organizing mesh routing, Nostr-native identity, Noise encryption, and transport-agnostic framing — making a custom routing protocol unnecessary.
    10|
    11|The NiceRF LoRa2021 module has two independent antenna ports: Sub-GHz (868 MHz, Pin 9) and 2.4 GHz (Pin 10). This allows dual-band operation on a single radio module, which is ideal for running two protocols simultaneously via time-division.
    12|
    13|We have proven components from prior work: sx1280-serial provides TDMA coordinator election, fragmentation/reassembly (SLIP + CRC-32, 128-byte fragments), and secp256k1 crypto identity binding in Rust. The gap is erasure coding (Wirehair fountain codes), which has not yet been integrated with the fragmentation layer.
    14|
    15|MeshCore (2.9k GitHub stars, active European community in UK/DE/Benelux) provides an established Sub-GHz LoRa mesh with geographic routing, repeater firmware, and coverage mapping tools (mapme.sh). Running MeshCore on the balloon's Sub-GHz band provides immediate community value: stratospheric coverage mapping and long-range message relay.
    16|
    17|TollGate provides a Cashu-based payment protocol for selling network access. It runs at ground stations with WiFi captive portals. The esp32-tollgate implementation also includes a Nostr relay, enabling async messaging.
    18|
    19|Nostr (NIP-01) events are small JSON documents with secp256k1 signatures. They fit naturally over LoRa links when kept short (~500 bytes for kind 0/1/7 events). A store-and-forward relay on the balloon allows disconnected ground stations to exchange messages through the balloon's flash buffer.
    20|
    21|## Decision
    22|
    23|Adopt a layered architecture using existing open-source components at each layer:
    24|
    25|| Layer | Protocol | Role | Runs On |
    26||-------|----------|------|---------|
    27|| L7 | TollGate + Nostr | Payment gating + async messaging | Ground station + balloon (store-and-forward) |
    28|| L6 | FIPS Noise XK | End-to-end encrypted sessions | Balloon + ground station |
    29|| L5 | FIPS mesh routing | Spanning-tree + bloom-filter discovery | Balloon + ground station |
    30|| L4 | UDP/IP tunnel | Transport over FIPS mesh | Ground station (balloon is relay) |
    31|| L3 | Erasure-coded fragmentation | Wirehair fountain codes + sx1280-serial fragmentation | Balloon + ground station |
    32|| L2 | TDMA dual-band scheduler | Time-shares LR2021 between Sub-GHz and 2.4 GHz | Balloon |
    33|| L1 | LR2021 radio | LoRa/FLRC dual-band | Balloon + ground station |
    34|
    35|### Dual-Band Allocation
    36|
    37|| Band | Frequency | Protocol | Pin | Antenna | Role |
    38||------|-----------|----------|-----|---------|------|
    39|| Sub-GHz | 868 MHz | MeshCore (EU preset: SF8, BW62.5, CR8) | Pin 9 | Wire dipole (8.6 cm legs) | Community mesh repeater + coverage mapping |
    40|| 2.4 GHz | 2.4 GHz | FIPS (LoRa/FLRC adaptive) | Pin 10 | Wire dipole (3.1 cm legs) | Mesh networking + Nostr transport + TollGate relay |
    41|
    42|MeshCore on Sub-GHz is integrated from day one, sharing the TDMA scheduler with the 2.4 GHz FIPS transport.

    49|  - Balloon stores events in SPIFFS/LittleFS FIFO buffer (~500 events = ~250 KB)

    51|- **Phase 3+**: Expand to DMs, long-form content, zap receipts

    86|## The Gap: Erasure Coding
    87|
    88|Wirehair fountain codes are the missing piece. Without erasure coding:
    89|- Every lost fragment requires ACK + retransmission (expensive at 300 km, 1 ms propagation)
    90|- With 30-37% packet loss (measured), retransmission storms degrade throughput
    91|
    92|With Wirehair:
    93|- Transmitter generates infinite encoded fragments from k originals
    94|- Receiver needs any k encoded fragments to decode (no specific fragment required)
    95|- No ACK round-trip needed — balloon blasts encoded fragments in TDMA slot, goes back to sleep
    96|- Transmit ~1.5x fragments for 35% loss (k=4 → send 6 encoded blocks)
    97|
    98|Integration point: between sx1280-serial's fragmentation layer and the LoRa PHY. Fragment format becomes:
    99|`[block_id (4B)] [seed/fragment_index (1B)] [k (1B)] [Wirehair-encoded payload]`

    1|# ADR 013: Cluster-Aware Stratorelay for MeshCore
    2|
    3|## Status
    4|
    5|Proposed
    6|
    7|## Context
    8|
    9|A balloon at 12 km altitude sees thousands of ground MeshCore nodes simultaneously across an ~800 km diameter footprint. Running the standard MeshCore repeater firmware would cause:
    10|
    11|1. **Packet storms**: Every flood packet from every ground node gets rebroadcast to every other ground node via the balloon, multiplying traffic by the number of visible clusters.
    12|2. **Channel saturation**: LoRa SF8/BW62.5 at 869.618 MHz has limited airtime. A dumb repeater seeing hundreds of nodes would exceed the 10% EU duty cycle.
    13|3. **Hidden node problem**: Ground nodes in different cities cannot hear each other but can all hear the balloon, causing simultaneous transmissions that corrupt data.
    14|
    15|The MeshCore community would benefit from stratospheric coverage (relay range from ~10 km ground-to-ground to ~700+ km via balloon) without their local networks degrading.
    16|
    17|MeshCore's `Mesh` base class provides virtual hook methods that allow subclassing without modifying the core framework:
    18|- `filterRecvFloodPacket()` — drop flood packets before processing
    19|- `allowPacketForward()` — control which packets get retransmitted
    20|- `onAdvertRecv()` — intercept node advertisements
    21|- `routeRecvPacket()` — override retransmission behavior
    22|
    23|Ground nodes must remain completely stock (standard MeshCore companion or repeater firmware). All intelligence lives on the balloon.
    24|
    25|A secondary benefit: the balloon can broadcast its GPS position and telemetry via standard MeshCore adverts and chat messages, providing a backup tracking path independent of internet, WSPR, or LoRaWAN.
    26|
    27|## Decision
    28|
    29|Implement a `StratoRelayMesh` class extending MeshCore's `mesh::Mesh` with cluster-aware filtering:
    30|
    31|1. **Passive cluster discovery**: Listen to ground node adverts and flood paths. Build clusters using union-find on observed forwarding relationships (if node A forwards node B's advert, they're in the same RF cluster).
    32|
    33|2. **Cluster head election**: For each detected cluster, elect one node as the communication gateway based on SNR quality, advert recency, and stability.
    34|
    35|3. **Cluster-aware filtering**: Only accept and re-bridge flood packets from cluster heads. Drop packets from non-head nodes (they're already handled by local ground flood).
    36|
    37|4. **Per-cluster bloom filters**: Use static bloom filters for scalable membership testing (~4 KB for 32 clusters of 100 nodes each, 1% FP rate). Custom implementation (no external library) to avoid dynamic allocation.
    38|
    39|5. **Zero-hop bridging**: Forward inter-cluster messages via `sendZeroHop()` — standard MeshCore packets that ground nodes process normally.
    40|
    41|6. **Balloon telemetry**: Broadcast GPS position in adverts, send telemetry via chat messages, respond to on-demand queries.
    42|
    43|### Memory Architecture
    44|
    45|```
    46|NodeTable:       256 nodes × 9 bytes = 2.3 KB (static array)
    47|UnionFind:       embedded in NodeTable (parent + rank per node)
    48|Bloom filters:   32 clusters × 125 bytes = 4.0 KB (static)
    49|Cluster heads:   32 × 7 bytes = 224 bytes (static)
    50|Total:           ~6.5 KB static DRAM
    51|```
    52|
    53|### MeshCore Extension Points
    54|
    55|| Virtual Method | Override Purpose |
    56||---|---|
    57|| `onAdvertRecv()` | Populate NodeTable + UnionFind from advert paths |
    58|| `filterRecvFloodPacket()` | Drop packets from non-cluster-head nodes |
    59|| `allowPacketForward()` | Enable bridging only between different clusters |
    60|| `routeRecvPacket()` | Selective retransmission via zero-hop to cluster heads |
    61|
    62|### Bloom Filter Decision
    63|
    64|Evaluated three libraries:
    65|- **ArashPartow/bloom** (`https://github.com/ArashPartow/bloom`): Uses `std::vector` (dynamic allocation). Header-only but violates MeshCore's "no dynamic allocation" principle.
    66|- **jvirkki/libbloom** (`https://github.com/jvirkki/libbloom`): C library, uses `malloc/calloc`. Server-oriented, overkill for 100-element filters.
    67|- **aappleby/smhasher** (`https://github.com/aappleby/smhasher`): Hash functions only, not a bloom filter.
    68|
    69|**Decision**: Custom `StaticBloomFilter` template class (~60 lines). FNV-1a hashing with multiple seed passes. Fixed-size bit array. Zero heap allocation. Matches MeshCore coding principles.
    70|
    71|### Build System Decision
    72|
    73|- **Flight firmware**: ESP-IDF (single MCU, shares radio with tracker via FreeRTOS mutex)
    74|- **Bench testing**: PlatformIO (`mesh-stack/meshcore-lr2021/`) for quick iteration
    75|- **Upstream PRs**: Two separate tightly-scoped PRs to MeshCore: (1) LR2021 variant, (2) StratoRelayMesh example
    76|
    77|### Single MCU Justification
    78|
    79|ESP32-C3 current tracker usage: 4.4 KB BSS, 134 KB flash code. Free: 258 KB DRAM, 3,700 KB flash. MeshCore core + StratoRelay additions: ~32 KB DRAM, ~100 KB flash. Well within budget.
    80|
    81|## Consequences
    82|
    83|### Positive
    84|- **No ground node changes**: Stock MeshCore firmware works as-is
    85|- **Community value**: Stratospheric range for MeshCore community without breaking local networks
    86|- **Free telemetry**: Balloon position visible on MeshCore map without internet
    87|- **Incremental**: Basic repeater works first (Phase 2a), clustering added on top (Phase 2b)
    88|- **Upstreamable**: StratoRelayMesh is a clean subclass, could become a MeshCore example
    89|
    90|### Negative
    91|- **Approximate clustering**: Bloom filter false positives cause over-filtering (safe — ground flood still delivers). Union-find from flood paths is heuristic, not exact topology.
    92|- **Unknown node density**: Real-world ground node counts at stratospheric range are unmeasured. Design is parameterized but needs tuning after first flight data.
    93|- **Advert GPS coverage varies**: Only companion radios with GPS include lat/lon in adverts. Dumb repeaters without GPS can't be geographically clustered. RF topology clustering (union-find on flood paths) is the primary mechanism.
    94|- **RAM for node table**: 256-node table is 2.3 KB. If actual density exceeds this, LRU eviction drops oldest nodes. This may cause clusters to be re-evaluated frequently in dense areas.
    95|
    96|### Risks and Mitigations
    97|
    98|| Risk | Mitigation |
    99||---|---|
    100|| Too few nodes for meaningful clustering | Fallback to normal repeater mode if < STRATO_MIN_CLUSTER_SIZE nodes per cluster |
    101|| Too many nodes (> 256) overwhelm NodeTable | LRU eviction + increase SNR threshold to only track strongest nodes |
    102|| MeshCore upstream rejects PR | Stratorelay runs as external PlatformIO project, doesn't need to be in MeshCore core |
    103|| Balloon advert triggers ground node flood echo | Set balloon advert interval to 60 min (configurable) vs default 5 min |
    104|| Cluster head goes offline | Re-election at next REBUILD_INTERVAL (5 min), packets temporarily unfiltered |
    105|
    106|## Reference Repositories
    107|
    108|| Repo | URL | Purpose |
    109||---|---|---|
    110|| MeshCore | `https://github.com/meshcore-dev/MeshCore` | Base framework, pinned to `companion-v1.15.0` |
    111|| ArashPartow/bloom | `https://github.com/ArashPartow/bloom` | Evaluated and rejected (dynamic allocation) |
    112|| jvirkki/libbloom | `https://github.com/jvirkki/libbloom` | Evaluated and rejected (malloc-based) |
    113|| aappleby/smhasher | `https://github.com/aappleby/smhasher` | MurmurHash3 reference (not used, FNV-1a sufficient) |

    9|

    11|

    15|

    17|

    23||-------|-------------------|-----------------|
    24|| Data link | WiFi AP+STA | LR2021 LoRa radio |

    30|| Identity | nsec → MAC/SSID/IP | nsec → radio identity (adapt) |
    31|| Nostr signing | nostr_event.c | SAME — reuse |
    32|| Mint health | mint_health.c | SAME — reuse |

    38|3. **Nostr event signing** — event creation + signature
    39|4. **Mint health checking** — mint status, accepted mints list
    40|5. **Geohash** — location encoding for balloon position
    41|6. **Config** — config.json, nsec loading

    44|
    45|1. **No WiFi AP/STA** — replaced by LR2021 radio init + TX/RX
    46|2. **No captive portal HTML** — replaced by radio protocol for payment exchange
    47|3. **No DNS server** — no DNS concept over LoRa

    61|

    63|

    67|

    69|

    73|
    74|- The captive_portal.c and dns_server.c files we kept are NOT needed for balloon. They remain useful for the original WiFi TollGate but should not be ported to the balloon radio variant.
    75|- A new **radio payment protocol** needs to be designed (ADR-002 candidate).

    81|1. What exactly does payment grant over radio? Relay time? Message quota? Bandwidth?
    82|2. Is there a session concept, or per-message payment?
    83|3. How does a client "discover" the balloon TollGate over LR2021? Beacon?
    84|4. Does the balloon relay Nostr events to ground, or is it purely local?

    1|# ADR-XXX: Balloon as Stratum Relay — E-Hash Mining Bridge
    2|
    3|## Status
    4|
    5|Proposed
    6|
    7|## Date
    8|
    9|2026-07-29
    10|
    11|## Context
    12|
    13|The balloon project has a LoRa radio link (Semtech LR1121 or similar) between the
    14|balloon (in the sky, with internet via STA WiFi) and ground-based stations.
    15|Felix has identified a use case: the balloon can serve as a **stratum relay
    16|bridge**, providing internet uplink for ground-based ASIC miners (Bitaxe, NerdMiner)
    17|in areas where the miners have no direct internet connection.
    18|
    19|The concept is called **E-Hash**: customers pay Ecash (via the existing TollGate
    20|Cashu payment system) for the bandwidth required to relay block templates
    21|(downlink) and nonce submissions (uplink) over LoRa. The balloon is NOT a hash
    22|engine — it never computes SHA256. It is a thin relay + payment gateway.
    23|
    24|### Existing Code Reuse
    25|
    26|The TollGate firmware already provides:
    27|- WiFi AP+STA, Cashu wallet, captive portal, HTTP API (`main/tollgate_api.c`)
    28|- Nostr identity, session management, firewall
    29|- The Phase 1 mining extraction (`mining-standalone/`) provides `stratum_client`
    30|  and `stratum_proxy` modules that build clean on ESP32-S3 (846KB, 0 warnings)
    31|
    32|### System Topology
    33|
    34|```
    35|  Mining Pool (Internet)
    36|         ↕  Stratum (TCP/WSS)
    37|    ┌────────────────┐
    38|    │   BALLOON      │  (ESP32-S3, in sky)
    39|    │  - stratum_client (upstream to pool)
    40|    │  - Cashu payment gateway (metered access)
    41|    │  - LoRa template broadcaster (downlink)
    42|    │  - LoRa nonce collector (uplink)
    43|    └───────┬────────┘
    44|            ↕  LoRa radio
    45|    ┌───────┴────────┐
    46|    │ GROUND BASE    │  (balloon LoRa terminal, RP2040 or ESP32)
    47|    │ STATION        │
    48|    │  - LoRa receiver (template → local stratum job)
    49|    │  - Local stratum server (serves Bitaxe)
    50|    │  - Share filter + uplink queue
    51|    └───────┬────────┘
    52|            ↕  USB / serial / local WiFi
    53|    ┌───────┴────────┐
    54|    │ BITAXE / ASIC  │  (hash engine, stock firmware)
    55|    │ MINER          │
    56|    │  - connects to local stratum server
    57|    │  - mines against relayed template
    58|    │  - submits shares locally
    59|    └────────────────┘
    60|```
    61|
    62|### Bandwidth Budget (LoRa)
    63|
    64|| Payload | Direction | Size (binary) | Frequency |
    65||---------|-----------|---------------|-----------|
    66|| Block template (Stratum notify) | Downlink (broadcast) | ~80-120 bytes | Every ~10 min (new block) |
    67|| Nonce submission (valid share) | Uplink | ~20 bytes | Per valid share |
    68|| Payment token (Ecash) | Uplink or side-channel | ~50-80 bytes | Per session/block |
    69|
    70|At LoRa SF7 (~100 bps effective): template broadcast takes ~8-12 seconds.
    71|At SF12 (~30 bps): ~30-40 seconds. Both fit within a 10-minute block window.
    72|
    73|Template is broadcast one-to-many — all ground stations in range receive it
    74|simultaneously. Nonce submissions are one-to-one uplink.
    75|
    76|## Decision
    77|
    78|The balloon implements a **Stratum Relay Service** with three components:
    79|
    80|### 1. Stratum Client (Balloon → Pool)
    81|
    82|Reuse the extracted `stratum_client` module from Phase 1. Balloon connects to
    83|a configured mining pool via STA WiFi (TCP/WSS). It acts as a standard stratum
    84|worker: receives `mining.notify` (block templates), submits `mining.submit`
    85|(valid shares from ground miners).
    86|
    87|The balloon registers ONE pool identity. All ground miners mine under the
    88|balloon's pool account. Revenue flows to the balloon's pool wallet.
    89|
    90|### 2. LoRa Template/Nonce Relay
    91|
    92|Define a new LoRa message protocol layer (separate from existing balloon
    93|telemetry packets):
    94|
    95|- **MSG_TEMPLATE** (downlink, broadcast): Binary-encoded block template fields.
    96|  Sent on every `mining.notify` from pool (new block or update).
    97|  All paying ground stations receive it.
    98|
    99|- **MSG_NONCE** (uplink, unicast): Binary nonce submission from ground station.
    100|  Contains: job_id(4B) + extranonce2(4B) + ntime(4B) + nonce(4B) = 16 bytes.
    101|
    102|- **MSG_PAYMENT** (uplink, unicast): Cashu token for bandwidth payment.
    103|  Ground station submits Ecash token to unlock template access.
    104|
    105|### 3. Cashu Payment Gateway (E-Hash)
    106|
    107|Reuse the existing TollGate Cashu wallet + payment API. Payment model:
    108|
    109|- **Per-block access**: Customer pays Ecash for N blocks of template delivery.
    110|  Each block = ~10 min window. Balloon tracks per-station credit balance.
    111|  Zero balance → template broadcast encrypted/keyed, station cannot decode.
    112|
    113|- **Share relay**: Included in per-block fee. Ground station submits shares
    114|  up to a rate cap (prevents flooding LoRa uplink with junk shares).
    115|
    116|The balloon's existing session manager (`main/session.c`) already does
    117|time-based MAC tracking and access control. Extending it to cover LoRa
    118|identity (per-station keys) is a natural fit.
    119|
    120|### Ground Base Station Role
    121|
    122|The ground base station is the critical translator:
    123|
    124|1. Receives LoRa template → decodes → constructs local Stratum `mining.notify`
    125|2. Runs a **local Stratum V1 server** (tiny, ~200 lines) on localhost
    126|3. Bitaxe connects to local server as if it were a normal pool
    127|4. Bitaxe submits shares → base station filters by difficulty → queues best
    128|   shares for LoRa uplink to balloon
    129|5. Base station manages Ecash payment: requests/maintains credit with balloon
    130|
    131|Bitaxe runs STOCK firmware — no modification needed. It sees a local stratum
    132|pool. The base station is transparent.
    133|
    134|## Invariants
    135|
    136|1. **Balloon never hashes.** No SHA256 computation on balloon. Pure relay.
    137|2. **Bitaxe runs unmodified firmware.** All intelligence in base station + balloon.
    138|3. **Template is broadcast, not unicast.** One LoRa transmission serves all stations.
    139|4. **No template without payment.** Cashu credit required to decode templates.
    140|5. **Only pool-difficulty shares go up.** Base station filters shares before uplink
    141|   to conserve LoRa bandwidth. Sub-target shares stay local.
    142|
    143|## Consequences
    144|
    145|### Positive
    146|
    147|- **Massive code reuse**: Cashu wallet, WiFi, identity, session management all
    148|  exist in TollGate firmware. Stratum client extracted in Phase 1. Only new
    149|  code is LoRa message encoding + ground base station stratum server.
    150|- **Bitaxe compatibility**: Stock firmware, zero modification. Any stratum-compatible
    151|  ASIC works (Bitaxe, NerdMiner, braiins OS miners).
    152|- **Revenue model**: Balloon operator earns Ecash for bandwidth. Miners get
    153|  internet-free pool access. Clean E-Hash economy.
    154|- **Scalable**: One template broadcast serves N ground stations. Uplink is the
    155|  only per-station bandwidth cost.
    156|
    157|### Costs
    158|
    159|- **Latency**: LoRa adds 8-40 seconds of template delivery latency vs ~100ms
    160|  direct internet. Miners work on stale templates for that window. Acceptable
    161|  for small miners (Bitaxe ~1-3 TH/s) — negligible revenue impact.
    162|- **Uplink contention**: Multiple ground stations submitting shares compete for
    163|  LoRa uplink airtime. Need backoff/Collision avoidance or TDM scheduling.
    164|- **Pool account centralization**: All miners mine under balloon's pool account.
    165|  Revenue trust model: balloon operator must distribute earnings honestly.
    166|  Ecash tokens provide accounting transparency.
    167|- **Ground base station complexity**: Needs a stratum server implementation.
    168|  Target: ~200-300 lines C on RP2040 or ~150 lines Python on a Pi.
    169|
    170|## Open Questions (for design session)
    171|
    172|### O1. Stratum V1 vs V2 upstream?
    173|
    174|V1 is simpler (JSON text protocol, widely supported, Bitaxe uses V1).
    175|V2 has better template distribution (binary, designed for relay scenarios)
    176|but adds protocol complexity. Recommendation: **V1 for initial implementation.**
    177|V2 can be layered later since the LoRa payload format is protocol-agnostic.
    178|
    179|### O2. Pool account / revenue distribution?
    180|
    181|Whose pool account? Options:
    182|- A) Balloon operator's account — all shares credited to operator, who
    183|     distributes Ecash to miners manually/automatically.
    184|- B) Per-miner pool accounts — balloon passes through stratum worker IDs.
    185|     Requires pool to support multiple workers under one connection (most do).
    186|
    187|Recommend B — standard stratum multi-worker. Balloon stratum_client uses
    188|`<pool_user>.<ground_station_id>` worker naming.
    189|
    190|### O3. Share difficulty filtering?
    191|
    192|Pool sets a share difficulty. At LoRa bandwidth, we cannot relay every share.
    193|Options:
    194|- A) Ground base station runs its own higher difficulty filter. Only shares
    195|     meeting a local threshold (e.g. 10x pool difficulty) go up. Fewer shares
    196|     relayed but each is more valuable.
    197|- B) Base station relays all pool-difficulty shares, accepts uplink contention.
    198|
    199|Recommend A — conserve LoRa bandwidth. Trade-off: slightly reduced share
    200|submission rate, but LoRa can't handle high share volume anyway.
    201|
    202|### O4. Template encryption / access control?
    203|
    204|Felix's model: customer pays Ecash for bandwidth. How do we enforce this?
    205|- A) Template broadcast in plaintext, but base station needs Ecash token to
    206|     authenticate uplink (nonce submission). Freeloader gets templates but
    207|     can't submit shares. Weak — they could mine for their own pool.
    208|- B) Template encrypted with per-session key. Base station gets decryption
    209|     key only after Ecash payment. Strong — no template without payment.
    210|
    211|Recommend B — use the existing session/key derivation (HMAC-SHA512 from nsec)
    212|to generate per-station template keys. Cashu payment unlocks key delivery.
    213|
    214|### O5. Balloon loses internet?
    215|
    216|When balloon STA WiFi drops (no internet):
    217|- Balloon cannot fetch new templates. Ground miners keep mining last known
    218|  template. Shares will eventually be rejected by pool (stale).
    219|- Balloon should cache last template + broadcast "stale" flag. Ground base
    220|  stations can choose to continue (waste of hashpower) or pause.
    221|
    222|Recommend: balloon broadcasts template with a TTL timestamp. Ground station
    223|stops mining after TTL expires without new template. Resumes when new
    224|template arrives.
    225|
    226|## Rollout / Implementation Phases
    227|
    228|TBD — implementation not yet started. Awaiting decisions on open questions O1-O5.
    229|
    230|Proposed phase structure (subject to approval):
    231|
    232|- Phase A: LoRa message protocol spec (template encoding, nonce format, payment)
    233|- Phase B: Ground base station prototype (RP2040: LoRa RX → local stratum server)
    234|- Phase C: Balloon stratum relay module (stratum_client → LoRa TX + Cashu gate)
    235|- Phase D: Integration test (balloon + base station + Bitaxe, end-to-end)
    236|
    237|## Notes
    238|
    239|- Phase 1 mining extraction (commit 9e40143) directly supports this architecture.
    240|  The `stratum_client` module is the balloon's upstream connection.
    241|  The `sw_miner`/`asic_miner` modules are reference for ground-side understanding
    242|  but are NOT deployed — Bitaxe runs its own firmware.
    243|- The existing TollGate session manager (`main/session.c`) does time-based access
    244|  control per MAC. Extending to LoRa station identity is a small addition.
    245|- LoRa radio hardware details (modulation, SF, bandwidth) are tracked in the
    246|  balloon-fresh repo's firmware track, not here. This ADR is protocol-level.
    247|- Felix's vision: E-Hash = Ecash + hashpower. The balloon provides infrastructure
    248|  (internet relay) as a metered Ecash service. Ground miners provide hashpower
    249|  and pay for uplink. This is the TollGate model applied to mining relay instead
    250|  of WiFi hotspot access.
